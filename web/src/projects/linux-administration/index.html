PROJECT OBJECTIVE

Operate Linux Servers End-to-End

This lab was designed around a realistic server lifecycle rather than isolated commands: establish a baseline, secure administrative access, prepare storage, operate an application service, restrict network exposure, and prove that the workload can be recovered from backup.

Provision→Secure→Store→Operate→Protect→Recover

01. SERVER PROVISIONING

Baseline & Inter-Node Connectivity

Reused a Vagrant/VirtualBox environment as a two-node Linux administration lab. Both nodes were assigned consistent hostnames, synchronized to Asia/Jakarta time, connected to the private lab network, and verified for bidirectional hostname resolution and ICMP connectivity.

linux01.lab — Ubuntu 22.04 LTS baseline and connectivity verification.
linux02.lab — CentOS Stream 9 baseline and connectivity verification.
02. USER & SSH ACCESS

Secure Administrative Access

Configured a dedicated administrative account on both distributions, using the Ubuntu sudo group and CentOS wheel group. Public-key SSH authentication was enabled while password-based SSH authentication was disabled. A shared appadmins group and setgid application directory demonstrate controlled group access.

sudo / wheelPublic KeyPassword SSH Disabledsetgid
Ubuntu privilege, effective SSH policy, and shared directory permissions.
ACCESS VERIFICATION

Cross-Distribution Controls

The same administrative model was validated on CentOS Stream with distribution-specific privilege groups. Root password authentication remains blocked by the effective PermitRootLogin without-password policy.

CentOS privilege, SSH policy, and group-inheritance verification.
03. STORAGE & LVM

Dedicated XFS Application Storage

Added a 5 GB virtual disk to the CentOS node, initialized it as an LVM physical volume, created vg_app, and provisioned lv_data as a 2 GB XFS filesystem mounted at /srv/appdata.

5 GB Disk→PV→vg_app→lv_data→XFS
Initial 2 GB application filesystem with test data.
ONLINE CAPACITY EXPANSION

2 GB → 4 GB Without Data Loss

Simulated increasing application storage requirements by extending the logical volume to 4 GB and growing XFS online. Existing application data remained intact after expansion.

4 GB LV/XFS after online expansion with existing data preserved.
UUID-based /etc/fstab mount verified after reboot.
04. SERVICE MANAGEMENT

Custom systemd Application Service

Deployed a small Python status service on TCP/8080 and managed it through a custom systemd unit running as a non-root account. The unit starts after networking, logs to journald, starts at boot, and uses Restart=on-failure.

Crash simulation: PID 6717 was killed; systemd detected the failure and recovered the service as PID 6851.
INCIDENT & TROUBLESHOOTING

Configuration Failure Recovery

An invalid ExecStart path was introduced to simulate a failed configuration change. systemctl status and journalctl exposed the missing file, after which the unit was corrected, reloaded, and returned to active state.

Service Failed→journalctl→Root Cause→Fix→Recovered
Failure, root-cause evidence, configuration correction, and service recovery.
05. FIREWALL & ACCESS CONTROL

Default-Deny Inbound Policy

Enabled UFW on the Ubuntu application node with a default-deny inbound policy. SSH remained available for administration, while TCP/8080 was restricted specifically to the CentOS node at 192.168.56.15.

Active firewall policy with source-restricted application access.
NETWORK VERIFICATION

Allowed Application Path

The CentOS node was then used to verify that the source-specific rule permits access to the application while the host firewall remains active.

linux02 successfully reaches the protected service on linux01:8080.
06. BACKUP AUTOMATION

Bash + systemd Timer

Created timestamped backups of the application and systemd configuration using a Bash script. A persistent systemd timer schedules recurring backup execution, providing multiple recovery points instead of overwriting a single archive.

RECOVERY TEST

Restore a Known-Good Backup

Recovery was tested by renaming the live application file, confirming the service failure, restoring a known-good archive, and verifying that the application returned to an active state and served HTTP requests again.

Application failure followed by successful restoration and service verification.

Lesson learned: the newest backup is not automatically a valid recovery point if it was created after a failure. Recovery should use a verified known-good archive.

WHAT I LEARNED

Operational Takeaways

The lab reinforced that Linux administration is not only about applying configuration. Each change needs verification, failure handling, and a recovery path. Testing negative cases—failed services, restricted access, storage growth, and restore procedures—made the environment more representative of day-to-day system administration.
